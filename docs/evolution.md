# Governed Evolution Engine

The Evolutionary Engine moves a capability through a governed lifecycle. It never executes source generated by an LLM. It receives an already-prepared handler plus immutable candidate bytes and controls when that handler may replace the active binding.

## Implemented lifecycle

    PROPOSED
       |
    VALIDATING
       |
    VALIDATED
       |
    AWAITING_APPROVAL
       |
    APPROVED
       |
    ACTIVATING
       |
     ACTIVE
       |
    ROLLING_BACK
       |
    ROLLED_BACK

A failed validation transitions to REJECTED. Reviewer decisions may transition to REJECTED or CHANGES_REQUESTED. A changes-requested proposal is terminal; revisions are submitted as a new proposal with a new artifact hash. A failed activation or rollback transitions to FAILED. Invalid transitions are rejected by the state machine.

## Immutable candidate artifacts

EvolutionaryEngine.propose requires non-empty bytes for the candidate artifact. ArtifactStore stores the candidate content-addressed by SHA-256. Repeated writes of the same content resolve to the same record. A read verifies both the stored size and digest.

The proposal preserves the previous ToolBinding, candidate ToolBinding, artifact record, registry generation and creator identity. In-memory artifact storage is provided for tests and development. Production should provide durable immutable object storage with access control, retention and integrity verification.

## Validation attestation

CandidateValidator receives both the prepared candidate handler and the exact ArtifactRecord. Its ValidationReport must include the candidate's SHA-256 and a unique validation ID. The engine rejects a passing report that omits or mismatches the artifact digest.

CandidateValidator is part of the trusted computing base. It must prove that the executable handler it prepares corresponds to the supplied artifact, run in an isolated environment and produce a reproducible report. The current package defines this contract but does not provide a container/VM sandbox, compiler, dependency resolver or build-provenance attestor.

## Human approval

A trusted approval gateway must authenticate the human and then issue an EvolutionApproval. The signed token binds:

- proposal ID;
- immutable artifact SHA-256;
- validation report ID;
- approver identity;
- issue and expiry times;
- one-time nonce.

HmacEvolutionApprovalVerifier verifies the signature, expiry, artifact/report binding, independent approver identity and nonce uniqueness. The helper sign_evolution_approval is a reference signer; it is not an identity provider. Never expose the signing secret to agents or model contexts.

The reference nonce cache is process-local. Production must use shared durable storage with atomic consume semantics so replay remains blocked across replicas and restarts.

## Activation and compare-and-swap

Activation first transitions the proposal to ACTIVATING, re-reads and verifies the immutable artifact, and asks ToolRegistry to replace the active handler only if its generation matches the generation captured at proposal creation.

A concurrent registry change causes the operation to fail closed. The candidate is not allowed to overwrite a newer version. The registry operation is atomic within the current process.

## Rollback

The previous ToolBinding remains attached to the proposal. rollback() restores it only if the registry generation still equals the generation produced by this proposal's activation. If another update has happened since activation, rollback refuses to overwrite it and the proposal becomes FAILED for operator reconciliation.

This is a reference in-process rollback of a registry binding, not a distributed deployment rollback. Production multi-process deployments need a durable release controller and a coordination mechanism that atomically updates shared routing/version metadata.

## Audit

Each lifecycle transition emits an AuditEvent containing proposal ID, creator or approver identity, action, candidate version and artifact hash. The default sink is in-memory and intended for tests. Production requires durable, tamper-evident audit storage and a transactional outbox or equivalent recovery strategy for failures between registry changes and audit persistence.

## Deliberate boundaries

- The engine does not execute LLM-generated code.
- It does not install dependencies, run arbitrary shell commands, push commits or deploy binaries.
- Human identity is authenticated by the external approval gateway, not by the HMAC signer.
- The test validator is intentionally simple; production validation must cover unit, integration, contract, security, dependency, adversarial and performance checks.
- The runtime only swaps an already-loaded ToolBinding. Building and attesting a handler from an artifact is the next integration boundary.
