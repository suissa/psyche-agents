# Governed Evolution Engine

The Evolutionary Engine moves a capability through a governed lifecycle. It never executes source generated by an LLM. It receives immutable candidate bytes and an already-prepared ToolBinding, validates the exact bytes in an isolated runner, requires signed human approval and performs CAS activation.

## Lifecycle

    PROPOSED
       |
    VALIDATING
       |
    VALIDATED
       |
    AWAITING_APPROVAL
       |
    APPROVED
       |
    ACTIVATING
       |
     ACTIVE
       |
    ROLLING_BACK
       |
    ROLLED_BACK

A failed validation transitions to REJECTED. Reviewer decisions may transition to REJECTED or CHANGES_REQUESTED. A changes-requested proposal is terminal; revisions must be submitted as a new proposal with a new artifact hash. Failed activation or rollback transitions to FAILED. Invalid transitions are rejected.

## Immutable candidate artifacts

ArtifactStore stores bytes by SHA-256. InMemoryArtifactStore is useful for tests. SQLiteArtifactStore provides local durable storage with WAL, FULL synchronous writes, content verification and restrictive database-file permissions. SQLite is intended for one host or multiple processes sharing a local durable filesystem; multi-host deployments should provide an object-store ArtifactStore implementation.

Each proposal preserves the previous ToolBinding, candidate ToolBinding, artifact record, registry generation and creator identity.

## Sandboxed validation

SandboxCandidateValidator adapts SandboxOrchestrator to the engine's CandidateValidator contract. The orchestrator runs a configured validation matrix and creates a report containing exact check names, failures and the artifact digest.

ContainerSandboxRunner executes trusted validation commands inside a digest-pinned Docker or Podman image. It disables network access, uses a read-only root filesystem and read-only candidate mount, drops Linux capabilities, enforces no-new-privileges, runs as a numeric non-root user, limits PIDs/CPU/memory/time/output and provides only a noexec temporary filesystem.

The engine rejects any passing report that omits or mismatches the candidate digest. A timeout, non-zero check result or sandbox runner failure blocks approval.

The container runner's image and commands are trusted deployment configuration. The candidate bundle is an opaque read-only file; the validation image is responsible for safe parsing, compilation and test execution. Rootless Podman is recommended. The container daemon remains part of the trusted computing base.

## Prepared artifact loading

PreparedArtifactLoader maps a verified artifact digest to a ToolBinding that has already been prepared by trusted application/build code. On activation, the engine resolves the exact approved digest and checks that the loaded manifest equals the candidate manifest before replacing the active registry binding.

The loader never imports, evaluates or executes artifact bytes. A production build pipeline must verify provenance and prepare the handler in a trusted process before staging it. The current loader catalog is in-memory; a process restart requires the release/bootstrap layer to re-register its trusted prepared handlers.

## Human approval and replay protection

A trusted approval gateway must authenticate the human before issuing an EvolutionApproval. The signed token binds proposal ID, immutable artifact SHA-256, validation report ID, approver identity, issue/expiry times and a one-time nonce. The verifier rejects self-approval, expired tokens, mismatched digests and replay.

InMemoryNonceStore is provided for tests. SQLiteNonceStore provides durable atomic nonce consumption across processes sharing a local database. Multi-host deployments need a shared transactional nonce store. Never expose the signing secret to agents or model contexts.

The HMAC signer is a reference primitive, not an identity provider. Application authorization must verify approver roles and separation of duties before token issuance.

## Activation and rollback

Activation re-reads and verifies the immutable artifact, resolves the prepared handler by digest, checks its manifest and replaces the active handler only if the registry generation equals the one captured at proposal creation.

The previous binding remains attached to the proposal. Rollback restores it only if the registry generation still equals the generation created by this activation. A newer registry update causes rollback to fail closed rather than overwrite the newer change.

This is an in-process registry operation, not a distributed multi-host release controller. Distributed production deployments need durable version metadata and coordination around routing and activation.

## Runtime health

RuntimeHealthMonitor consumes error-rate, p95-latency and contract-failure samples supplied by the host application. Configured thresholds can trigger RecoveryController automatically, or degradation can be reported without rollback by disabling auto_recover.

The monitor does not collect telemetry itself. Production must connect an observability adapter and define service-specific thresholds, evaluation windows and safety policy.

## Audit and persistence boundaries

The ArtifactStore and optional nonce store have SQLite implementations. Evolution proposal state, prepared handler catalog and default audit sink are still in memory. Production must add durable proposal state, tamper-evident audit storage and transactional coordination between registry changes and audit persistence.

## Deliberate boundaries

- The engine does not execute LLM-generated source.
- It does not install dependencies, run arbitrary shell commands, push commits or deploy binaries.
- The trusted build/loader pipeline must prepare the handler for the exact candidate artifact.
- The container daemon and pinned validation image are trusted computing-base components.
- The engine swaps an already-prepared ToolBinding; a complete source-to-binary build and release pipeline is not supplied.


## Durable audit and release coordination

Pass `SQLiteAuditLog` as the engine's `audit` sink to preserve proposal creation and lifecycle transitions across process restarts:

```python
audit = SQLiteAuditLog("./var/psyche-audit.sqlite3")
engine = EvolutionaryEngine(registry, audit=audit)

# Periodically export this tuple to a separately controlled system.
sequence, chain_head = audit.checkpoint()
if not audit.verify_chain():
    raise RuntimeError("evolution audit integrity check failed")
```

The audit sink stores canonical JSON records in an append-only table. Each entry hashes the preceding entry and its own payload. Concurrent writers serialize through SQLite's `BEGIN IMMEDIATE` transaction. The checkpoint (sequence and chain head) should be exported to a separately controlled immutable store; without an external anchor, an administrator able to rewrite the entire database can recompute the chain. SQLite WAL and FULL synchronous mode are enabled, and the database file is restricted to owner access where the filesystem supports POSIX permissions.

The release boundary is represented by the `ReleaseCoordinator` protocol. `SQLiteReleaseCoordinator` provides a durable implementation with:

- per-target exclusive leases and monotonic fencing tokens;
- lease renewal and explicit release;
- generation-based compare-and-swap before publishing a new release record;
- idempotency keys that return the original result for an identical retry and reject key reuse with a different payload;
- a hash-chained release event log written in the same transaction as lease and release state.

Example:

```python
coordinator = SQLiteReleaseCoordinator("./var/releases.sqlite3")
lease = coordinator.acquire("payments-api", "release-controller-1", ttl_seconds=30)
snapshot = coordinator.commit(
    lease,
    expected_generation=0,
    version="1.1.0",
    artifact_sha256="<sha256-of-trusted-prepared-artifact>",
    idempotency_key="payments-api-1.1.0",
)
```

A fencing token prevents a worker whose lease expired or was superseded from committing after a newer worker has acquired the target. Generation CAS prevents publishing against a state that changed after it was read. The idempotency key handles retries after an uncertain response; reusing it for a different owner or release payload fails.

**Deployment boundary:** this SQLite coordinator supports multiple processes sharing one durable local database and filesystem. It is not a multi-host consensus system, and SQLite over NFS or an unreliable network filesystem is not supported. Multi-host deployment must provide a server-backed implementation of `ReleaseCoordinator` with transactional lease/fencing and generation-CAS semantics. The `EvolutionaryEngine` still performs an in-process `ToolRegistry` swap; an application release adapter must connect the coordinator to its actual deployment/routing system. It must not treat a coordinator record as proof that code was built, signed or deployed.

Proposal history can be made durable immediately by injecting `SQLiteAuditLog`; prepared handlers and active in-process bindings still need a trusted bootstrap/catalog on restart. The audit log is a durable event history, not a serializer for Python handler objects.
